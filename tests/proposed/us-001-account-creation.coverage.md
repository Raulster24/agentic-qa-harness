## Exploration notes

Verified end-to-end against the live app at http://localhost:3333.

Key app quirks:
- The base URL redirects to /en (landing) and /en/start; the home/overview after auth is /en/home with heading 'Welcome to Ghostfolio'.
- Registration dialog requires TWO gating steps: (1) tick the 'I understand' Terms checkbox then 'Continue'; (2) the in-dialog 'Create Account' button stays DISABLED until the token is acknowledged by clicking 'Copy to clipboard'. This was the non-obvious part, without the copy click the button never enables. If the browser's clipboard permission is unavailable in CI, the click handler may still enable the button (it did during exploration), but watch for clipboard permission flakiness; if it fails, grant clipboard-read/write permissions in the Playwright config.
- There are two header buttons after auth; the account/avatar menu is the LAST header button. I used header button .last() with a comment because the avatar button has no accessible name. The menu item is 'Log out'.
- The generated token is a 128-char hex string read from the 'Security Token' textbox inputValue(), tests capture it at runtime rather than hardcoding.
- Both 'Create Account' (page button + dialog button) share the same accessible name; within the registration flow they appear sequentially so getByRole name resolves correctly at each step. The sign-in 'Sign in' name is shared between the header button and the dialog button; in AC4/AC5 the header button is clicked first (opens dialog) then the dialog 'Sign in' button, Playwright resolves to the enabled one after fill. If strict-mode duplicate-match errors arise, scope the dialog locator with getByRole('dialog').

Gaps / not covered: 'Stay signed in' checkbox behavior, token copy-to-clipboard actual clipboard contents, and social (Google) login were out of scope.
